# Проектная работа модуля 1. Чтение, парсинг и анализ данных в Rust

Вы завершили изучение первого модуля. В этой работе вам предстоит применить полученные знания на практике, создав законченный проект на Rust.

**Тема:** обработка финансовых данных в Rust (чтение, парсинг, конвертация и сравнение финансовых данных).

**Суть проекта** Вам нужно разработать библиотеку для работы с финансовыми операциями и два консольных приложения, которые будут использовать эту библиотеку. Проект должен быть оформлен как единый Cargo-пакет.

Вы соберёте все базовые темы в одну нормальную практическую задачу: модули, структуры, `enum`, работа с `Read`, ошибки, тесты, `Cargo`, владение, заимствование и обычная прикладная логика.

**Плановое время на выполнение:** примерно 10-12 часов с оформлением, тестами и проверкой.

Ниже представлен подробный разбор задачи с конкретными требованиями к функциональности и структуре проекта, за которым следуют пошаговый план реализации и критерии успешной сдачи.

## Задание

Соберите один Cargo package:

- библиотека в `src/lib.rs`;
- приложение `converter` в `src/main.rs`;
- приложение `comparer` в `src/bin/comparer.rs`.

Библиотека должна читать данные через `Read`, писать через `Write`, поддерживать форматы `csv`, `text`, `bin` и работать через единое внутреннее представление транзакции.

`converter` конвертирует данные между форматами (файл или `stdin` → `stdout`), а `comparer` сравнивает два файла после парсинга в транзакции.

Подробный маршрут выполнения и критерии результата смотрите ниже в разделе **«Пошаговое выполнение»** и чек-листе **«Требования к результату»**.

## Что именно вы реализуете

### 1. Библиотека

Соберите библиотеку, которая читает/пишет операции через `Read`/`Write`, умеет парсить и конвертировать форматы, сравнивать транзакции и возвращать понятные ошибки.

### 2. Приложение `converter`

Сделайте CLI-приложение в `src/main.rs`, которое принимает источник данных и форматы, а всю логику парсинга/записи передаёт библиотеке.

### 3. Приложение `comparer`

Сделайте приложение в `src/bin/comparer.rs`, которое парсит два файла через библиотеку, сравнивает транзакции и при различии показывает позицию и поле расхождения.

Вам предстоит создать единый Cargo-пакет, содержащий несколько компонентов.

**Библиотека (ядро проекта):**

- Чтение финансовых операций из любого источника, реализующего `Read`.
- Запись операций в любой приемник, реализующий `Write`.
- Поддержка трёх форматов данных: CSV, текстовый и бинарный.
- Приведение всех форматов к общему внутреннему представлению транзакций.

**Два консольных приложения:**

- converter — читает данные из файла или стандартного ввода, конвертирует между форматами, выводит результат.
- comparer — читает два файла, парсит их через библиотеку и сравнивает списки транзакций.

**Требования к структуре:**

- Один package (не workspace и не несколько отдельных пакетов).
- Библиотека: `src/lib.rs`.
- Конвертер: `src/main.rs`.
- Сравниватель: `src/bin/comparer.rs`.

Проект не должен быть разбросан по workspace и отдельным пакетам. Вместо этого нужен один аккуратный пакет с библиотекой в `src/lib.rs`, приложением-конвертером в `src/main.rs` и приложением для сравнения в `src/bin/comparer.rs`.

## Поддерживаемые форматы

В проекте нужно поддержать три формата.

### 1. `csv`

```text
date,category,kind,amount
2026-04-01,salary,income,120000
2026-04-02,rent,expense,40000
```

Первая строка — заголовок. Дальше идут записи.

### 2. `text`

```text
2026-04-01;salary;income;120000
2026-04-02;rent;expense;40000
```

Одна строка — одна операция.

### 3. `bin`

Это бинарный формат. Его точную схему вы определяете сами, но она должна быть:

- детерминированной;
- документированной в `README.md`;
- пригодной для чтения и записи через `Read` / `Write`;
- одинаково понятной и библиотеке, и обоим приложениям.

В бинарном формате важно не делать “магический набор байт без правил”. Схема должна быть явной: например, с заголовком, количеством записей, длинами строковых полей и фиксированным способом хранения чисел.

## Минимальная доменная модель

Внутри библиотеки должно быть единое представление транзакции. Именно через него должны проходить и конвертация, и сравнение.

У каждой транзакции обязательно должны быть:

- дата;
- категория;
- тип операции;
- сумма.

Тип операции лучше выразить через `enum`, а не через сырую строку.

## Что считается одной и той же транзакцией

При сравнении файлов одинаковыми считаются только те транзакции, у которых совпадают все поля:

- дата;
- категория;
- тип операции;
- сумма.

Сравнение должно идти **после парсинга**, а не по исходному тексту или бинарным данным.

## Как именно сравнивает `comparer`

Здесь важно не оставлять двусмысленность. В этой работе считаем так:

- порядок транзакций важен;
- количество транзакций должно совпадать;
- сравнение идёт поэлементно, от первой записи к последней;
- если в одном файле есть лишняя запись, это уже несовпадение;
- если записи отличаются, утилита может остановиться на первом различии и показать его.

Пример сообщения о несовпадении может быть таким:

```text
Транзакции отличаются на позиции 3: amount: 6500 != 7000
```

## Рекомендуемая структура проекта

Ниже нормальный ориентир, который хорошо ложится на материал модуля:

```text
ypbank-tools/
├── Cargo.toml
├── README.md
└── src/
    ├── lib.rs
    ├── main.rs # converter
    ├── format.rs
    ├── error.rs
    ├── model.rs
    ├── csv_format.rs
    ├── text_format.rs
    ├── bin_format.rs
    └── bin/
        └── comparer.rs
```

Если разложите библиотеку немного иначе, это нормально. Главное, чтобы структура была внятной и чтобы логика форматов, ошибок и общего API не была свалена в один огромный файл.

## Пошаговое выполнение

### Шаг 1. Создайте package и базовую структуру

- создайте новый публичный репозиторий;
- создайте один Rust package;
- подготовьте библиотеку, `converter` и `comparer`;
- добавьте `README.md`.

### Шаг 2. Опишите типы данных

- создайте структуру одной операции;
- создайте `enum` для типа операции;
- создайте `enum` для форматов;
- создайте тип ошибки для библиотеки;
- для библиотечных ошибок используйте свой `enum`, реализуйте `Display` и `std::error::Error`.

### Шаг 3. Реализуйте чтение и запись форматов

- библиотека должна принимать любой источник, реализующий `Read`;
- библиотека должна уметь писать данные в любой приёмник, реализующий `Write`;
- реализуйте чтение и запись для `csv`, `text` и `bin`;
- некорректные данные должны возвращать ошибку, а не тихо ломать результат.

### Шаг 4. Соберите общее API библиотеки

- библиотека должна уметь читать список транзакций в общем формате;
- библиотека должна уметь записывать этот список в нужный формат;
- библиотека должна уметь конвертировать данные через общее представление;
- библиотека должна уметь сравнивать два списка транзакций и сообщать о первом различии.

### Шаг 5. Соберите приложения

- `converter` должен читать данные из файла или `stdin`, принимать входной и выходной формат, писать результат в `stdout`;
- `comparer` должен читать два файла, знать формат каждого и выводить понятный результат сравнения;
- оба приложения должны использовать одну и ту же библиотеку, а не дублировать парсинг и запись.

### Шаг 6. Добавьте тесты

Минимальный набор:

- тест на успешный парсинг `csv`;
- тест на успешный парсинг `text`;
- тест на успешный парсинг `bin`;
- тест хотя бы на одну ошибку для каждого формата;
- тест на конвертацию между форматами;
- тест на `comparer` для совпадающих данных;
- тест на `comparer` для различающихся данных;
- хотя бы один тест через `Cursor`, чтобы проверить работу через абстрактный ввод.

### Шаг 7. Проверьте проект перед сдачей

Перед отправкой обязательно прогоните:

- `cargo fmt`
- `cargo check`
- `cargo test`

## Ограничения и Инструменты

### Что можно использовать

- `std::io::Read`, `BufRead`, `BufReader`, `stdin`, `File`, `Cursor`;
- `std::io::Write`;
- `Vec`, `HashMap`, итераторы;
- свои `struct`, `enum`, `impl`, `match`;
- `Result`, `Option`, оператор `?`;
- ручной разбор аргументов через `std::env::args()`.

### Что здесь не требуется

- `serde` и внешние библиотеки для парсинга;
- `clap` и продвинутый CLI-парсинг;
- async / await;
- несколько package или workspace;
- GitHub Actions;
- сложная политика версий зависимостей;
- оптимизация под огромные объёмы данных.

### Что ожидается от документации

- у каждого публичного типа и каждой публичной функции библиотеки должен быть `///`-комментарий;
- обычно достаточно 1-3 строк;
- в комментарии достаточно коротко описать назначение и возможные ошибки;
- doctest для этой работы не обязателен.

## Требования к результату

### Что обязательно должно быть

- один Cargo package с библиотекой и двумя bin-приложениями;
- библиотека работает с абстрактным вводом через `Read` и выводом через `Write`;
- библиотека умеет читать и писать `csv`, `text` и `bin`;
- библиотека переводит данные между форматами через общее представление транзакции;
- `converter` работает через библиотеку;
- `comparer` работает через библиотеку;
- есть свои понятные типы ошибок;
- библиотечные ошибки реализуют `Display` и `std::error::Error`;
- в библиотеке нет `unwrap`;
- публичные типы и функции библиотеки покрыты короткими `///`-комментариями;
- есть тесты на успешные и ошибочные сценарии;
- проект собирается и проходит `cargo test`;
- в репозитории есть `README.md` с инструкцией по запуску.

### На что будем обращать внимание

- проект не расползается по структуре без причины;
- логика чтения, записи и сравнения не дублируется в бинарных приложениях;
- `Read` и `Write` действительно используются как абстракции, а не всё намертво привязано к `File`;
- сравнение файлов сделано после парсинга, а не посимвольно;
- ошибки читабельны;
- в коде нет лишнего клонирования там, где оно не нужно;
- тесты проверяют реальное поведение, а не просто “что-то запускается”.
